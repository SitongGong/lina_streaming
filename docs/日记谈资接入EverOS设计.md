## 1. 核心设计决策

### 决策 1：方案 B「日记直检 + 话题做标签」（已定）

不走"话题为必经枢纽"（方案 A）。日记条目直接进 EverOS、**话题ID 作为每条的元数据标签**，
同时支持两种召回：
- **语义召回**：当前对话 ≈ 日记内容（用户提到话题时）。
- **话题过滤召回**：按话题ID精确取（主动找话时）。

### 决策 2：话题识别也用 EverOS 检索，不用 controller 枚举（已定）

> 解决"上百话题，controller 没法每个 LLM 判、规则塞不进"的问题。

话题卡本身是可检索实体（ID + 标题）。所以**话题识别 = 检索话题卡库**，不是分类规则：
```
当前对话上下文 → 向量检索话题卡库 → 召回最相关 2-3 个话题ID
```
话题再多也不怕（向量召回，非规则枚举）。controller 只做轻判断（要不要找谈资/要不要
主动），**不碰具体话题分类**。

### 决策 3：self_facts 瘦身（已定方向）

self_facts 现混了两类：
- **静态人设**（身份/喜好/厌恶/经历）→ 本就该在人设里，EverOS 人设检索已覆盖，
  **砍掉**（留着是冗余，也是 2000 轮压测"张冠李戴"的根因之一）。
- **动态承诺/近况**（"答应帮用户留意治猫过敏的法子"）→ 运行时产生的 agent 状态，
  **暂留**；将来走 EverOS agent add 提取（需 LLM，等 122B，先不动）。

## 2. 数据进 EverOS（都走 agent 轨道、写 md、零 LLM）

复用已验证的 agent_skill 机制（写 md → cascade embedding 索引，不需大模型）。
两类 collection，靠 skill name 前缀区分：

### 2.1 日记条目 → agent_skill（前缀 `diary_`）
每条"记忆"写一个 skill：
- `name`: `diary_M2026-01-01-01`
- `description`: 记忆标题（如"整理年初的废旧纸张与账目"）
- 正文 content：事实骨架 + 正文 + 情绪 + 时间地点（供向量检索）
- **话题ID 关联**：写进 content（如末尾加 `话题: A02-04 C06-01 …`），让按话题ID
  的 keyword/语义检索能命中。（EverOS agent_skill 无自定义 filter 字段，话题ID
  以文本形式进 content 做可检索标签。）

### 2.2 话题卡 → agent_skill（前缀 `topic_`）
每个被日记引用过的话题卡写一个 skill：
- `name`: `topic_A02_04`
- `description`: `A02-04 最近小变化 · 最近生活中出现的小调整`
- content：话题标题 + 大类用途说明（从 索引.md 的大类描述继承）
- 只导**被日记引用过的话题**（4828 引用去重后的集合），空壳话题不导。

> 注：日记 collection 和话题 collection 都在 `agent_id=lina` 下，检索时靠
> `name` 前缀或 query 措辞区分；如需硬隔离，可用不同 agent_id（如 `lina_diary`/
> `lina_topic`），评审时定。

## 3. 检索链路（统一走话题层，两级 EverOS 检索）—— 已定

**被动（用户提话题）和主动（找话头）走同一条链路**：都先到话题层，再到日记。
好处：链路统一、可控，被动场景也从预设话题取材，不乱发挥。

```
当前对话上下文（用户问题 + 近 N 轮）
  → controller 轻判断：这轮要不要找谈资 / 要不要主动找话？（不判具体话题）
  → 要 → ① EverOS 检索【话题卡库】(agent_id=lina_topic, vector) → 得 2-3 个话题ID
        → ② 按话题ID 检索【日记库】(agent_id=lina_diary, vector，话题ID 在 content 可检索)
        → 取最相关 2-3 条日记 → 注入「莉娜的相关经历/谈资」块
```

- 两个话题各对应多篇日记时，第 ② 步按相关度排序取 top，**不全塞 prompt** ——
  EverOS 压缩召回的价值所在。
- controller 只判"要不要"，**不枚举话题**（话题交给 EverOS 检索），所以话题再多也不怕。
- 主动发言时同链路（与现有 proactive 逻辑结合）。

### controller 的角色（轻判断）
- 新增/复用一个轻顾问：判"这轮要不要找谈资 / 要不要主动找话"。
- **不判具体话题**。

## 4. 注入点（不碰 CORE 人设、不碰主模型 prompt）

- 日记/谈资检索结果 → 注入到一个**新的或复用的**记忆块（如「莉娜的相关经历/谈资」），
  与现有「角色设定参考」「关于用户的记忆」并列。
- 注入位置在 `character.py` 的 `_build_user_content`，与人设/用户记忆同款，
  **主模型 prompt 模板不动**。

## 5. 开放问题决议（已定）

1. **agent_id 分开**：日记 = `lina_diary`，话题 = `lina_topic`，硬隔离。人设仍 `lina`。
2. **日记粒度**：一条"记忆"一个 skill（细粒度召回更准，上千 skill 可接受）。
3. **触发**：**controller 判定要找谈资后才检索**（不是每轮都检索，省开销）。
4. **话题卡范围**：只导**被日记引用过的**话题（策划未写完，后续补全增量再导）。
   空壳话题不导。话题 content 暂用 ID+标题+大类用途；若召回不准，再用关联日记摘要反哺。
5. **rerank 暂不用**：统一 vector 检索（与人设一致）。日后量大召回不准再议。
