# Controller 加速：合并微顾问（定量报告）

## 背景
Controller 的 LLM 决策层原本每轮并发发 **20 个单字段微请求**（每个判一个字段）。
墙钟 ≈ 最慢那个请求；请求越多，越容易撞上网络抖动/重试 → 尾延迟大、波动大。
方案：把 20 个按判断逻辑合并成 **4 组**（场景模块 / 风格长度 / 行为微调 / 检索决策），
每组一次 LLM 调用问出该组所有字段 → 每轮 4 个并发请求。
（实现为新增文件 merged_experts.py / merged_controller.py，**未改动原 20 并发版**。）

## 速度对比（50 条复杂输入，controller=Claude Haiku，强制走 LLM 路径）

| 指标 | 分开版（20 并发） | 合并版（4 请求） | 提速 |
|---|---|---|---|
| 平均 | 1.74s | 1.40s | **+19%** |
| 中位 P50 | 1.50s | 1.40s | +7% |
| P90 | 2.40s | 1.50s | **+38%** |
| **P95（尾延迟）** | **3.40s** | **1.50s** | **+56%** |
| 最慢 | 4.50s | 1.50s | +67% |
| 波动区间 | **1.2s ~ 4.5s** | **1.3s ~ 1.5s** | 长尾基本消除 |

**结论**：平均延迟降约 1/5；**P95 尾延迟从 3.4s 压到 1.5s（-56%）**，延迟从大幅波动
变为稳定 1.5s 左右。对用户体感而言「稳定 1.5s」优于「平均快但偶发 4.5s」。

## 回复质量对比（20 组场景，各跑到主模型最终回复）
判优劣不看「两版判得像不像」（一致率会误导），看**莉娜最终回复是否合理**：
- ~15 组：两版回复都合理，平手。
- 2 组：合并版**更好**（细节更丰富）。
- 3 组：合并版略弱——仅「安抚类」少了一句温柔铺垫，回复本身仍合理（仍会关切反问）。
- **无一组判崩/答错。**

→ 合并版回复质量与分开版基本持平，唯一短板是安抚类语气稍硬（可通过把「安抚」字段
单独判 或 在合并 prompt 里强调安抚来补齐，提速不受影响）。

明细见 docs/merged_vs_separate_replies.json（20 组逐条 plan + 回复）。

## 取舍
| | 速度 | 回复质量 |
|---|---|---|
| 分开版（现状） | P95 3.4s，波动大 | 安抚类更到位 |
| 合并版 | **P95 1.5s，稳定** | 基本持平，安抚类略硬 |

**建议**：合并版提速实打实且回复不崩，值得采用；若在意安抚体验，把「安抚（user_vent）」
字段从合并组单独拎出（4 组→「1 单 + 3 合」），可兼顾速度与质量。

## 复现
```
python tests/bench_merged_vs_concurrent.py     # 50 条速度对比
python tests/compare_merged_replies.py         # 20 组最终回复对比 → JSON
```
