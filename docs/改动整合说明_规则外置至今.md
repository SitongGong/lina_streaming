## 1. 规则/prompt 全外置到文件

**问题**：controller 的规则文字散在 Python 代码里（experts.py 的 19 个 advisor 判定规则、
rule_router 的正则、composer 的约束句、controller 的 stage 策略），改一句话要改代码、重启。

**做法**：全部搬到 `prompts/` 下的文件，代码改为从文件加载：
- 主模型 prompt → `prompts/main/`（behavior_rules / mood_format / segment_protocol / system_template / proactive / farewell / continue_instruction 等 7 个 txt）
- 规则层正则 → `prompts/controller/rules.json`
- 19+ 个 advisor 判定规则 → `prompts/controller/advisor_rules.json`
- 主动发言分级策略 → `prompts/controller/proactive_stages.json`
- 约束句 → `prompts/controller/constraints.json`

**原理**：在 `app/controller/_prompts.py` 加了一个**全局 override 层** + JSON 字段加载器
（`load_json_value(file, dotpath)`）。加载时先查 override（网页改的），没有再读磁盘文件。
代码里只保留「兜底默认」，文件缺失/损坏也不崩。

**代码**：`_prompts.py`、`experts.py:_apply_advisor_rules`、`rule_router.py:_load_rule_patterns`、
`controller.py:_load_proactive_stages`、`composer.py:_load_constraints`。

## 2. 全接入网页提示词编辑器（98 个组件）

**做法**：网页「提示词」tab 原本只管 9 个组件，扩到 **98 个**——把上面所有文件 + JSON
内部每个字段拆成**细粒度可编辑组件**（key 形如 `controller/advisor_rules.json#lenient_typos.decision_rules`）。

**原理**：override key 用「文件路径#JSON点路径」寻址；网页保存时写入全局 override 层，
`load_json_value` 命中即返回 → **改即时生效，无需重启**。组件列表由读 JSON 自动生成，
以后往 JSON 加规则，网页自动出现新条目。

**代码**：`web.py:PROMPT_COMPONENTS` + `_generate_json_components()` + `_default_value()` +
`_sync_controller_overrides()`。

## 3. 规则层关键词精简

**问题**：规则层正则太泛，误伤明显——"我想吃蛋糕"被当兴奋点、"拜托你帮我"被当告别、
"好吃得要命"被当发泄、含 "ai" 两字母的任何词被当现代请求。

**做法**：删掉会误伤的词（甜点整组、单字"拜"、"ai" 两字母、"老粉/回来了"、"要命/好惨"、
"古文"、"手机/电脑"等泛词/现代词/网络词），模糊场景交给 LLM 判（LLM 判得更准）。

**代码**：`prompts/controller/rules.json`。回归验证：误判全修，该命中的仍命中、无退步。

## 4. 记忆 bug 修复（莉娜自我清单）

**问题（领导反馈）**：2000 轮压测后「多了很多不知道的记忆 / 张冠李戴 / 降智」。
根因：self_facts（莉娜自我事实清单）把**每轮即兴编的一次性遗物剧情**（铁片、盒子、铜币）
当成「莉娜的稳定经历」记下，跨对话重新注入后细节对不上 → 张冠李戴。

**做法**：改提炼 prompt（`prompts/controller/self_facts.txt`）——只记「一个月后还成立」的
长期稳定事实，**绝不记一次性剧情/具体遗物，宁缺勿滥**；并清洗了现有被污染的清单。
**验证**：200 轮压测 0 污染，且稳定事实（喜好/承诺）仍正常记。

## 5. 用户长期记忆（新功能）

**问题**：聊上百轮后莉娜把**用户讲的事**忘了/记混/编造。根因：之前只有「莉娜自我清单」，
用户讲的事全靠 BM25 检索原始对话——早期对话滑出窗口后 BM25 又检不回来。

**做法（与 self_facts 对称）**：
- `app/user_facts.py`：UserFactsStore，按桶（身份/喜好/厌恶/关系/经历/近况/约定）存用户
  讲过的稳定事实，per-user 跨会话，上限 40 条防膨胀。
- `prompts/controller/user_facts.txt` + `controller.update_user_facts`：后台 LLM 概括，
  只记用户长期稳定事实（**名字必记**），不记莉娜的事/一次性事/不编造。
- 注入：每轮在 prompt 加「关于用户的记忆」块；**清单短（≤40）时整份注入**（不靠 BM25，
  避免「换个说法问就检不到」），主模型自己从完整清单找。
- `web.py`：chat 时加载注入 + 滑出窗口后台提炼。

**验证**：87 轮真实对话提炼 → 新会话聊 21 轮引用旧事，名字/研究方向/感情/家庭/AGI 全部
正确记起、会主动调用、不编造。

## 6. 主动发言叠加用户记忆

**问题**：主动发言「挑话头」只看最近 8 轮历史，但四级策略里「翻更早的话题」需要更早的
上下文——8 轮里没有，它无米下锅。

**做法**：挑话头（`pick_proactive_topic`）时**把 user_facts 清单也喂进去**（用户长期讲过的事），
让它能从「用户提过但很久没聊」的事里挑话头，不局限最近 8 轮。

**验证**：最近历史只有「天气」（没料），挑话头正确从清单捞出「团子+考研」→
「团子最近怎么样？有没有陪你复习考研？」。

**代码**：`controller.py:pick_proactive_topic`（加 user_facts 参数）、
`prompts/controller/proactive_topic.txt`（加「用户长期讲过的事」段）、`character.py:_run_proactive`。

## 7. 用户说再见后不再主动发言（你点名要的）

### 现象
用户告别（如截图「算了，先聊这些吧，我去休息了，拜拜」），莉娜温柔收尾后，**却又主动
找话**「诶，休息得怎么样了？」——告别后停主动没生效。

### 根因
第一版实现：前端判「用户告别」用的是 `plan.matched_rule === 'plain_farewell'`。
但 `plain_farewell` 是**规则层正则**，要求**整句几乎就是「拜拜」**才命中。截图那种
**长句**告别走的是 LLM 路径、不命中 plain_farewell → 前端没把会话标记为「已告别」→
主动发言计时器照常触发。**所以是漏判：只认纯「拜拜」，认不出长句里夹的告别意图。**

### 修复（原理）
不再只靠规则层那个窄正则，改成 **controller 输出一个专门的 `user_farewell` 字段**，
两条路都能判出告别意图：
1. **规则层**：`plain_farewell` 命中（纯「拜拜」等）→ `user_farewell=True`。
2. **LLM 路径**：新增一个 `user_farewell` 微顾问，专门判「用户这轮是否在告别/想结束」，
   **明确长句里夹的告别意图也算**（「先聊这些吧我去休息了」「不说了回头聊」）。
3. **前端**：改成认 `plan.user_farewell`（而非 matched_rule）→ 为真就置 `conversationEnded=true`
   → `maybeProactive()` 开头检查到它就**不再主动找话**；用户下次发消息时自动解除。

### 验证
- 纯「拜拜」（规则层）→ user_farewell=True ✅
- 长句「算了…先聊这些吧…我去休息了…拜拜」（走 LLM）→ True ✅（之前漏的，现在能识别）
- 正常聊天 → False（不误判）✅

### 代码
- `schema.py`：加 `user_farewell` 字段
- `experts.py`：加 `user_farewell` BoolAdvisor（判长句告别意图）
- `controller.py:_merge`：接 `user_farewell`；`rule_router.py`：plain_farewell 命中时置 True
- `chat.html`：前端改认 `data.plan.user_farewell`（line ~2427），`maybeProactive` 开头 `if (state.conversationEnded) return`

## 8. Controller 提速（合并 advisor，实验）

**问题**：controller 每轮并发发 **20 个单字段微请求**，墙钟 ≈ 最慢那个；请求越多越容易
撞上网络抖动/重试 → 尾延迟大、波动大（P95 到 3.4s）。

**做法**：把 20 个按判断逻辑合并成 **4 组**（场景模块/风格长度/行为微调/检索决策），
每组一次 LLM 调用问出该组所有字段 → 每轮 4 个并发请求。
**未改原版**：新增 `merged_experts.py` / `merged_controller.py`，与原版并存。

**定量结果**（50 条复杂输入，Claude Haiku）：
| 指标 | 原 20 并发 | 合并 4 请求 | 提速 |
|---|---|---|---|
| 平均 | 1.74s | 1.40s | -19% |
| **P95 尾延迟** | **3.40s** | **1.50s** | **-56%** |
| 波动区间 | 1.2~4.5s | 1.3~1.5s | 长尾基本消除 |

**质量**：20 组最终回复人工核验，~15 平手、2 更好、3 略弱（仅安抚类语气稍硬），**无判崩**。

**网页开关**：右上角「合并advisor(提速)」勾选框，任何登录用户可切（全局生效、下一轮起效），
用于 A/B 体验。切换走 `/api/controller_mode`，并强制复位前端发送状态防卡死。

**取舍**：提速实打实、回复不崩，可采用；若在意安抚体验，可把「安抚」字段单独判。
明细见 `docs/controller_merge_speedup.md` 和 `docs/merged_vs_separate_replies.json`。
